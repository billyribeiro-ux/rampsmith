# ADR-256: Backup metadata is signed with Ed25519; the public key is committed

- Status: Accepted
- Date: 2026-10-22
- Stream: R1 backup hardening
- Refines: Closes finding M2; refines ADR-172

## Context

The restore picked the newest object in the bucket and trusted its metadata. Anyone who can write the bucket (a leaked token) could add a future-dated or forged object, or replace an archive, and a restore would use it. Integrity needs an anchor outside the bucket.

## Decision

- `backup.sh` signs `<base>.meta.json` with Ed25519 (`openssl pkeyutl -sign -rawin`, OpenSSL 3) using `BACKUP_SIGNING_KEY`, a sealed Railway variable (base64 of PKCS#8 DER). Upload order: archive, signature, metadata; the metadata is the commit marker. The run reads both back and verifies.
- The public key per environment is committed at `infra/backup/signing/<env>.pub.pem`, generated by `infra/backup/signing/generate.sh` (refuses to write the private key inside the repository).
- `bk_verify_backup` checks the signature, the signed environment, the key name, that the creation time matches the key stamp, that it is not in the future (10-minute skew), and the signed size and sha256 against the downloaded archive. `restore.sh --object` requires `--verify-key`.
- The newest backup is chosen by parsed timestamp, among complete ones. `list-backups.sh` reports complete, incomplete, future, misfiled and invalid. Retention never counts or keeps an object stamped after the run time plus skew.
- Rotation: `generate.sh --rotate`; older backups verify against the key committed at their date (git history).

## Consequences

An attacker with the bucket token can destroy backups the lock prevents, but cannot make a restore accept a forgery.

## Rejected alternatives

- Object checksums only: stored beside the object they protect.
- age-signed metadata: age has no signatures.
