# ADR-244: The element mapper and its confidence model

- Status: Accepted
- Date: 2026-10-19
- Stream: W4 / WS-14 (`ws/patch-r2`; `packages/liquid-patch`, `src/map/`)

## Context

PLAN §12 maps a rendered element to its source in five steps, with "exactly one candidate above
0.9 confidence → mapped". It leaves open what a confidence is made of, how a section wrapper
becomes a file, what to do with section groups and static sections, and what to return when a
candidate exists only outside the files the page renders. The corpus contract (ADR-203) scores
the answer: mapped at 0.9 or more to the golden span is correct, to another span is a failure of
the gate on its own, and anything below 0.9 is "not mapped" (reviewed by a person or the AI
tie-break, PLAN §12 step 4).

## Decision

1. **The mapper is pure.** `new Mapper(files).map(finding)` reads theme files from a
   `Map<path, text>` and a description of the rendered element from the scanner (tag,
   attributes, collapsed text, ancestors up to `<html>`, the previous siblings and the number of
   following siblings when collected). No network, browser, clock or randomness: the same input
   gives the same answer. The corpus runner supplies the description from Chromium
   (`packages/corpus-tools/src/browser/check.ts`).
2. **Order of the steps.**
   1. A page-wide rule maps to its element in the layout: `html-has-lang`, `html-lang-valid`
      and `html-xml-lang-mismatch` to `<html>`, `bypass` to `<body>`. One such element: 0.97;
      several: `needs_review` with all of them. The layout is the template's `layout` key
      (ADR-243 point 6).
   2. The nearest ancestor whose id starts with `shopify-section-` names a section instance.
      shopify.dev documents `section.id` as "dynamically generated by Shopify" for sections in
      JSON templates and as the file name for a static section
      (https://shopify.dev/docs/api/liquid/objects/section), and documents no wrapper id
      format, so (as ADR-205 finding 6 advised) the mapper relies on the `__<key>` suffix:
      every `__` of the id is tried as the split, and the key is looked up in the page's
      template JSON and in every section group JSON (`sections/*.json`); an id without `__`
      is a static section if `sections/<id>.liquid` exists. Candidates are de-duplicated by
      file and pointer.
   3. The files the element can come from are the **render closure** of the instance's section
      file: snippets by `{% render %}` and `{% include %}` with a string literal, theme blocks by
      `{% content_for 'block', type: '<literal>' %}`, and for `{% content_for 'blocks' %}` the
      block types the instance's JSON lists (nested blocks included). A target named by a
      variable marks the closure `dynamic`. Outside any section the closure starts from the
      layout.
   4. Rich text the theme prints maps to store data first (ADR-246).
   5. Otherwise the element is searched for in those files (point 3 below). A style rule
      (`color-contrast`, `link-in-text-block`, `target-size`, `rs-focus-indicator-missing`)
      then maps its cause with the cascade (ADR-245), using the element found here as
      `rendersFrom`.
3. **A source element can have produced the rendered one only if** all of this holds (see
   `src/map/elements.ts`): (a) the tag names are equal; (b) every attribute the source names
   outside a Liquid tag is on the rendered element and its value fits the source text with
   `{{ }}` and `{% %}` matching anything, whitespace in `class`, `style` and `d` collapsed, and
   character references decoded; an attribute inside a Liquid tag may be absent; (c) every
   rendered attribute is in the source, unless the start tag prints attributes through Liquid
   (`{{ block.shopify_attributes }}`); (d) each run of plain text directly inside the source
   element is in the rendered text; (e) the source's ancestor elements within the same file
   occur, in order, among the rendered ancestors. A plain `{{ settings.x }}` or
   `{{ section.settings.x }}` value is read from the theme's JSON and must be what was
   rendered. Elements that fail only (e) are kept apart as `elsewhere`.
4. **Confidence is a count of agreeing static evidence, nothing else.** Points: an `id` 2, class
   tokens up to 3, any other static attribute 1, a setting lookup equal to its stored value 1,
   plain text 1, and up to 2 for ancestors with a static class or id. A single candidate with at
   least one point maps at `min(0.99, 0.90 + 0.02 * min(points, 5))`; with no point (tag only)
   at 0.75. The score is lowered, never raised, by doubt: to at most 0.85 when the closure was
   `dynamic` and the points are under 3, and to at most 0.85 when the match needed the lenient
   pass (the JSON disagreed with what was rendered: a market override, an edit since). So
   nothing is mapped at 0.9 or more on the position of a file or the order of elements.
5. **Several candidates are never mapped.** Two or more matches return `needs_review` with
   every candidate at 0.5, for the AI tie-break of PLAN §12 or a person. One match that exists
   only in files the page does not render returns `needs_review` at 0.6. No match returns
   `unmapped`.
6. **Same-file twins.** Candidates in the `elsewhere` set with an identical description in the
   same file (birch's hidden mobile cart link, ADR-205 finding 7) are returned as `identical`
   spans: the same fix applies to them and the runner applies it, so the hidden copy is not left
   empty.

## Consequences

- Confidence is a heuristic score, not a calibrated probability. It was tuned on the corpus it
  is measured against (ADR-249 says so); the tarn tests (`test/mapper.test.ts`) exercise the
  doubtful branches on a second, hand-written theme, and a release should re-measure on themes
  not seen while writing it.
- Elements printed inside loops map to the one source element; a fix applies to every iteration,
  which is what a source fix is.
- A snippet rendered by several parents maps to the snippet. A fix there changes every caller;
  recipes that need a per-caller label (ADR-248) get it from the caller's `params`.
- JavaScript-created elements have no source in the theme's Liquid and come back `unmapped` or
  `needs_review`.

## Rejected alternatives

- Ranking by file or document order, or by the first match: a wrong answer above 0.9 fails the
  mapping gate by itself.
- Matching the rendered HTML text against the Liquid source with diffs: attribute and text
  wildcards are exactly what the AST gives; a textual diff fights the Liquid.
- Making the AI tie-break part of the package: the package stays deterministic and offline; the
  API owns the model call (PLAN §12 step 4).

## Plan correction

PLAN §12, "Mapping a rendered element to its source", steps 2 and 3. Replace

> 2. The page's JSON template (`templates/*.json`) maps that section id to a section type, which names `sections/<type>.liquid`.
> 3. Within that file and every snippet or block it renders (`{% render %}`, `{% content_for 'blocks' %}`), the Liquid AST is searched for HTML element nodes matching the element's tag, static attributes and class tokens. Attribute values produced by Liquid output act as wildcards.

with

```markdown
2. The page's JSON template (`templates/*.json`), the section group JSON (`sections/*.json`) or, for a static section, the file name, maps that section id to a section type, which names `sections/<type>.liquid`. The wrapper id's prefix is not documented; the key after `__` is what is relied on (ADR-244).
3. Within that file and every snippet or block it renders (`{% render %}`, `{% include %}`, `{% content_for 'block' %}`, `{% content_for 'blocks' %}`), the Liquid AST is searched for HTML element nodes matching the element's tag, static attributes, class tokens, text and ancestors. Attribute values produced by Liquid output act as wildcards, except a plain setting lookup, which must equal the stored value. Confidence counts the static evidence that agreed (ADR-244).
```
